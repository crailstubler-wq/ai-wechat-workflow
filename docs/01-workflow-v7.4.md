## 一、总览

```
选题(Step 1) → 写作设计(Step 2) → 标题定稿(Step 3) → 撰写(Step 4) → 封面(Step 5)
    ↓              ↓                ↓               ↓              ↓
 四维评分+三塔   角度/类比/反差     A/B/C 三型      长文(双文风)    文生图
 用户拍板        用户确认           用户拍板         用户审核        用户确认
                                                        ↓
                                   HTML排版(Step 6) → 预览gate(Step 6.5) → 推送(Step 7) → 评论巡查(Step 8)
                                            ↓                ↓                  ↓              ↓
                                      全内联HTML         层次清单核对          脚本建草稿      读者反馈对账
                                      8项兼容            用户确认OK          用户群发        四级判定
```

**核心原则**：AI 驱动执行，人工审核把关。每步结果持久化到磁盘（按 `content/YYYY-MM-DD-{slug}/` 组织）。

## 二、八步详细流程

### Step 1：选题（四维评分 + 三塔归类）

**执行人**：主理人亲做（选题定调是工作流核心，不外派）。

1. **采集热点**：WebSearch / 热点聚合工具，时间窗锁死**近三天**。
2. **四维评分**（各 1-5 分，记录每条热点的「来源 URL + 时间 + 可信度」，避免凭印象筛）：
   - **时效** — 是否落在近三天窗口内
   - **影响** — 行业 / 读者波及面大小
   - **契合** — 是否贴合公众号主线与品牌调性
   - **延展** — 能否接暗线连续剧或衍生后续选题
3. **确定选题类型**（三塔，见第三节），匹配切入角度。
4. **用户选定**。

**输出**：选题标题 + 核心角度 + 三塔类型。

### Step 2：写作设计（占质量 60%）

**执行人**：主理人亲做（策略层，品牌调性灵魂，不外派）。

1. 列出 **3 个常规角度**，主动避开 → 找第 4 个反差点。
2. 储备 ≥ 1 个跨领域类比（生活化、读者可感，用于帮助理解而非替代论证）。
3. 设计情绪曲线（忌连续否定型）。
4. 写入 `angle.md`（角度 / 类比 / 节奏 / 信源表）。

**铁律**：不能跳过 Step 2 直接写正文——角度 / 类比 / 节奏占质量 60%。

### Step 3：标题定稿（A/B/C 三型，用户拍板）

**执行人**：主理人按三原则把关（可派 copywriter 初拟，见 `docs/02` §3.4）。

- 动笔前先给 3 组（A/B/C 型）标题，**用户选定**再写正文，禁止跳过。
- 标题质量三原则（见第四节）硬约束。

### Step 4：撰写正文

**执行人**：派 copywriter（长文写作核心能力）。

- **观点型（khazix 风格）**：纯汉字 ≥ 3000（用 `sed 's/[[:space:][:punct:]]//g' article.md | wc -m` 确认）。
- **技术解读型（第四支柱）**：4000-6000 含标点，客观复盘风，必须引一手信源。
- 开场 3 段内必须建立悬念，不能以事实堆砌开头。
- 写完 mid-check 回看 `angle.md`，不跑偏。

### Step 5：封面图

**执行人**：派 image-creator（文生图）。

- 规格：1280×720 横版，16:9。
- 风格：与品牌色板一致（见第七节）。
- 提示词必须英文（生图模型对英文理解更好）。
- 生成后主理人 `cp` 为 `cover.png` 用于推送（脚本默认读 `cover.png`）。

### Step 6：HTML 排版（微信兼容）

**执行人**：主理人亲做（私有标签 / 8 项兼容检查，成员无此专长）。

- **模板化铁律**：写前先 `cp content/templates/article_template.html content/YYYY-MM-DD-xxx/article.html`，替换 `[占位]` 文字、删不需要的块；**禁止每期从零写 HTML**。
- 全内联样式，无 `<style>` / `class`。
- 写前先读一篇已发布的同类型文章结构做对照（防格式走样）。
- 8 项兼容自检（见第六节，扩展为「8 项兼容自检」）。
- 排版密度强制对齐 #6：排版必须包含 H2 红色左边框章节标题、关键词红色强调（`<strong style="color:#c41e3a">`）、术语 code 高亮满篇、浅蓝 `#f0f7ff` 要点卡片、蓝色左边框引用块、流程图（步骤框 + ↓ 箭头）、盾/矛多色块对比（浅绿 `#f0fff4` 盾 / 浅红 `#fff5f5` 矛）、信源块、结尾金色标记。缺任一层级需补齐。
- 结尾两件套铁律（见第五节）。

**输出**：`article.html`。

### Step 6.5：排版预览核对（硬 gate）

**执行人**：主理人亲做（推前最后一关，任一层级缺失/漂移都回 Step 6 修，不进 Step 7）。

- 推前必须打开 `article.html` 预览，主动通栏列出「层次清单」，请用户核对：
  - H2 红色左边框章节标题数（应 ≥ 文内逻辑分段数）
  - code 术语高亮数（应满篇分布）
  - 流程图（步骤框 + ↓ 箭头）是否齐全
  - 色块层级（浅蓝要点卡 / 蓝边引用块 / 盾矛多色块 / 信源块）是否齐备
  - 结尾金色标记（写在最后 + 关注我深色卡）是否在
- **用户确认 OK 后才进 Step 7**；任一层级缺失或漂移 → 回 Step 6 修，不推。

### Step 7：API 推送

**执行人**：主理人亲做（技术脚本）。

- 从 `metadata.json` 读取 title / digest（**禁止硬编码**）。
- 刷新 token → 上传封面拿 `thumb_media_id` → 创建草稿 → **用户手动群发**。
- 订阅号 API 无法自动群发（48001），只能建草稿。
- 文末公众号名片由脚本自动追加（`<DATA_ID>` 占位，勿在「关注我」卡挂外链）。
- **推前定版决策**：明确推「带提示词版」（`article.html`，供用户复制生图）还是「清理版」（`article_published.html`，删 3 个锚点块）；用户要生图 → 带提示词版，生图上传完 → 再推清理版终稿。
- **清理脚本规则**：必须按 section 分块只删含锚点块，禁正则非贪婪吞删（曾误删开头橙卡 + 正文）。
- **旧草稿清理策略**：每次重推前提示用户删上一版草稿；或记录 media_id 清单，群发时明确「用最新 media_id X，前 N 份丢弃」。

### Step 8：发布后评论巡查（Step 7 后固定动作）

**执行人**：主理人亲做，群发后 1-3 天触发，不阻塞 Step 1-7。

- 用户在后台看到评论截图 / 转述 → 主理人逐条对账原文。
- 读者反馈四级判定框架（见 `docs/05`）：事实错误 / 表述模糊 / 纯情绪 / 同构盟友。
- 输出《反馈对账笔记》，沉淀为红队审查教材。

## 三、选题三塔模型

每篇选题必须先归到三类之一，三类穿插发布，不连续发同类。

| 类型 | 占比 | 目的 | 关键动作 |
|------|:---:|------|---------|
| **流量选题** | 40% | 拉新、涨粉 | 追公域热点、行业大事 |
| **人设选题** | 30% | 信任、粘性 | 展示个人经历 / 价值观 / 工作日常 |
| **转化选题** | 30% | 深度认可、促活 | 纠正认知、揭露盲区、反常识观点 |

**技术解读**为第四内容支柱，与三塔正交（同一热点既可发观点型也可发技术解读型），低频（周 ≤ 1 篇）。

## 四、标题质量三原则 + 公式池

### 三原则（硬约束）

1. **信息密度** — 必须含主体 + 判断，读者扫一眼知道讲什么；不能为短而短砍掉上下文。
2. **品牌辨识** — 有从业者视角、有态度、敢说真话（放在别的号上也成立的标题缺乏辨识度）。
3. **情绪多样** — 不连续多篇用否定型；同型标题也要换角度（质疑 / 好奇 / 愤怒 / 共鸣交替）。

### 公式池（10 类，扩维后收敛）

先用 10 类通用公式各出 2-3 个标题扩成素材池，再用三原则收敛到 A/B/C 三型交用户拍板：

① 结果承诺 ② 问题解决 ③ 悬念好奇 ④ 反差对比 ⑤ 利益点 ⑥ 权威/数据 ⑦ 观点态度 ⑧ 警示威胁 ⑨ 身份共鸣 ⑩ 场景代入

公式池只扩思路，最终仍走 A/B/C 三型 + 三原则硬收敛，不堆 30 个让用户选。

## 五、HTML 结尾格式铁律

- 结尾只用两张深色卡片：**写在最后** + **关注我**。彻底去掉「一句话总结」卡片。
- **「关注我」整块居中**：section 与内部 `<p>` 均加 `text-align:center`。
- 深色卡片配色固定 `#1a1a2e` + 金边 `#f5a623`，仅用于这两张结尾卡。
- **关注我卡不挂外链**：不放任何 `/s/` 文章详情链接，关注引导完全由推送脚本自动追加的公众号名片承担。
- **开头导语橙卡（固定）**：悬念开场白用浅橙卡包裹 `<section style="background:#fffaf0;border:1px solid #f5a623;border-radius:8px;padding:18px 16px;margin:0 0 24px;">`，只装「悬念导语」2-3 段；连续剧 / 暗线定位放文章中部。
- **关注我卡标准文案（固定三行）**：标题「关注我」+ 品牌人格句（如「一个做了快十年 AI 安全的老朋友。」）+ 价值主张（如「每周拆一个真案例，带你看清 AI 时代的安全账。」）+ 口号（如「记录 AI 时代的每天。」）。禁止只写「关注我，记录 AI 时代的每天。」缩水版。
- **结尾两卡边框风格**：统一 `border-left:4px solid #f5a623`（非全边框圆角）。

## 六、8 项兼容自检（HTML 必过）

| # | 检查项 | 必须为 |
|---|--------|--------|
| 1 | `class` 属性 | 0 个 |
| 2 | `<style>` 标签 | 0 个 |
| 3 | flex 布局 | 0 个（改用 `<table>`） |
| 4 | grid 布局 | 0 个（改用 `<table>`） |
| 5 | `<ul>/<li>/<ol>` | 0 个（改用 `<p>•`） |
| 6 | `<section>` | 仅在深色卡片中使用 |
| 7 | background | 必须用 `background-color` |
| 8 | 表格布局 | 必须用 `<table>` |

> 微信过滤 `class` 和 `<style>` → 全内联；`flex` → `table`；`font-weight:数字` → `bold` 关键字；`<ul>/<li>` → `<p>+•`；`linear-gradient` → `<strong>+color`。

**8 项兼容自检扩展项（新增）**：

- class / `<style>`块 / `<ul><li>` / flex / font-weight 数字 / gradient / DOCTYPE 外壳 / HTML 注释 全部为 0；
- `section` 开闭平衡（开标签数 == 闭标签数）；
- **code 内禁写 font-size（必须继承正文 16px）**——在 code 块里强制写固定字号会破坏微信内阅读体验，术语高亮一律只着色不加字号。

**字数检查**：`sed 's/<[^>]*>//g' article.html | wc -m` ≥ Markdown 原文 95%，否则内容可能被截断。
**正文区**：不含标题 / 公众号名 / 日期（由 API 字段渲染）。

## 八、6 条质量铁律

1. 不能跳过 Step 2 直接写正文 — 角度 / 类比 / 节奏占质量 60%。
2. 不能用技术圈内部类比 — 非技术读者看不懂。
3. 不能以事实堆砌开头 — 开场 3 段内必须建立悬念。
4. 不能字数不足 — 写完用 `sed 's/[[:space()[:punct:]]//g' article.md | wc -m` 确认区间。
5. 不能自我感觉良好 — 写完找 1 个最明显的缺点，主动提出修改。
6. 不能写到一半跑偏 — mid-check 回看 `angle.md`。

## 九、推送技术要点与踩坑速查（去敏）

**技术要点**

- 凭证存 `<PROJECT_DIR>/config/.env.credentials.yaml`（务必 gitignore）。
- 标准推送脚本读取 `metadata.json` 的 title / digest，**禁止硬编码**。
- 调用微信 API 的 Python 内必须 `os.environ.pop()` 清空代理变量；curl 必须绕过代理：`NO_PROXY="*" HTTPS_PROXY="" HTTP_PROXY=""`。
- 封面图先上传永久素材获取 `thumb_media_id`；脚本默认读目录内 `cover.png`。
- 订阅号无法 API 群发（48001），草稿箱 + 手动群发。

**常见错误码**

| 错误码 | 原因 | 解决 |
|--------|------|------|
| 40164 | IP 不在白名单 | 用户后台更新 IP 白名单 |
| 45003 | 标题超长 | 缩到 15 字内 |
| 42001 | token 过期 | 脚本自动刷新 |
| 48001 | API 权限不足 | 订阅号只能建草稿，手动群发 |
| 中文乱码 | 编码问题 | `ensure_ascii=False` + UTF-8 |

**踩坑速查（去敏）**

- 微信有时把出口 IP 识别为 `::ffff:x.x.x.x`（IPv4 映射 IPv6），纯 IPv4 白名单偶发不匹配，可试填 `::ffff:x.x.x.x` 或 `/24` CIDR。
- 双栈机器：curl 走 IPv6、微信 API 走 IPv4，**以微信报错返回的 IP 为准**，勿用 curl 看到的 IP 加白名单。
- 出口 IP 极不稳定（运营商轮换），白名单需频繁更新；**每次以脚本报错回显的 IP 为准**。
- 文中配图若走外部生图工具（如 GPT），可把英文 prompt 内联进 Markdown / HTML 对应位置，推送草稿后由用户复制去生成、上传、插入并删除提示词块，避免内置生图水印与微信 SVG 过滤冲突。
